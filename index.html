3 · 汇编结果专区 —— 四个地址逐个讲

每条按「这是什么（文字）→ 关键汇编（代码）→ 说明什么（效果）」展开。代码全部经过本地 capstone 5.0.9 独立反汇编复核，与仓库 CI 产物一致。

工具链：/il2cpp/read_mem 取原始字节 → 落 raw/*.txt → GitHub Actions 跑 tools/disasm.py（capstone）→ 出 out/*.asm 逐条汇编 + 立即数扫描。纪律：手解禁止入结论——先落字节过机器，再讨论语义。

① 构造函数 · TrainingCommandEntity..ctor @0x7547a5e304

这是什么：造「训练命令实体」的函数——游戏每次生成训练选项时，把命令 ID、演目增量字典、事件标志三样装进对象。约 500 字节。

; 参数落位（capstone 实测）
0x7547a5e3f4  str   w22, [x20, #0x10]   ; 参数2 → +16  CommandId
0x7547a5e4d0  bl    #0x7543427748       ; 调 thunk 造字典 ←旧手解误作 0x70e43844
0x7547a5e4d8  str   x0,  [x20, #0x18]   ; 字典返回值 → +24
0x7547a5e4d4  and   w8,  w19, #1        ; 参数4 取最低位
0x7547a5e4dc  strb  w8,  [x20, #0x20]   ; → +32  IsUpperTrainingEventOccurred
0x7547a5e4f8  ret                        ; 函数体止于此

说明什么：三个字段偏移（+16 / +24 / +32）全部实锤；字典来自外部调用一次成型，构造函数里没有内联常量（立即数扫描为空）；中途还有一层全局缓存（首次构造和后续复用走不同路径）。这也排除了「增量在构造时算死」的假设。

② 三连 thunk · 字典构造入口 @0x7543427748

这是什么：三个长得一模一样的「转发壳」，每只 84 字节，紧挨着排。自己不算任何东西，只搬寄存器然后尾跳。构造函数调的是第一个。

0x7543427748  str   x30, [sp, #-0x30]!
0x7543427754  ldr   x8, [x3, #0x38]     ; 延迟初始化探测
0x7543427764  cbnz  x8, #+0x28          ; 已初始化则跳过
0x7543427770  bl    #0x7542aa40c8       ; 类初始化
0x7543427778  ldr   x4, [x8, #0x18]     ; 第4参 = 初始化结果 +0x18
0x7543427798  b     #0x754342a684       ; 尾调用 → 真实实现

三胞胎出口（capstone 复核全对）：
  0x7543427748 → 0x754342a684   ← 构造函数用的这只
  0x754342779c → 0x754342aa38
  0x75434277f0 → 0x754342adec

说明什么：这一层零业务逻辑（立即数扫描为空）。整条地址链是 构造 0x7547a5e4d0 → thunk 0x7543427748 → 实现 0x754342a684。另两只 thunk 推测是同模式的其他重载（只有地址证据，暂无调用方证据）。

③ 通用集合装配壳 · 真实实现 @0x754342a684

这是什么：IL2CPP 泛型字典的「装配车间」——不是演目逻辑。双延迟初始化、三重空值检查、接口方法表线性查找，一应俱全。

; 形参落位
0x754342a698  ldr   x8, [x4, #0x38]
0x754342a69c  mov   x21, x4       ; 静态源
0x754342a6a4  mov   x22, x2       ; 包装对象
0x754342a6ac  mov   x20, x0       ; CommandId
; 三重空值检查（任一为空 → 抛异常）
0x754342a6dc  cbz   x20, #+0x260
; 接口方法表线性查找
0x754342a734  ldrh  w9, [x8, #0x12e]   ; 方法数
0x754342a73c  ldr   x10, [x8, #0xb0]   ; 表起点
0x754342a748  cmp   x11, x1            ; 逐项比对
; 收尾：拿到方法指针后虚调用
0x754342a778  ldp   x8, x1, [x0]
0x754342a780  blr   x8

说明什么：证实「演目增量在字典构造层计算」的假设被排除——它只装配集合。这是上游追查六条排除链的第五条（前四条：getter 内计算 ✗ / 构造内联常量 ✗ / MDB 表 ✗ / Define 静态表 ✗）。

④ 极简 getter @0x7547a565e0（流水线自测样本）

这是什么：8 字节、两条指令——直接返回对象 +0x18 处的字段，正是演目字典。构造函数写进 +24，这里就从 +24 读出，读写对上了。

0x7547a565e0  ldr   x0, [x0, #0x18]   ; 返回 this+24 的字典字段
0x7547a565e4  ret

说明什么：读字典这个动作没有任何计算——想找增量来源，必须去「写字典的那一侧」，于是有了上面 ①→②→③ 的追查链。

3.5 · 验证结论 —— 对了什么、错了什么

验证方法：本地 capstone 5.0.9 独立解码全部 4 份原始字节文件，与仓库文档断言逐条比对（与 CI 同引擎、不同环境，交叉验证）。

✅ 复核通过（全部一致）

  • 构造函数三个字段偏移 +0x10 / +0x18 / +0x20 ✓
  • 构造函数 bl #0x7543427748（CTOR-VERIFIED 修正后的值）✓
  • thunk 三胞胎结构与三条尾跳目标 a684 / aa38 / adec ✓
  • 装配壳形参落位、三重空值检查、接口方法表线性查找、blr 虚调用收尾 ✓
  • 构造函数体止于 0x7547a5e4f8 ret，与 ret_offsets 口径一致 ✓

⚠️ 发现两处文档内伤（原仓待修，不影响汇编本身）

1. README 关键地址表未同步
README.md 第 47 行仍写着旧手解错误值 0x70e43844（标着「手解·待复核」），但 docs/CTOR-VERIFIED.md 早已用 capstone 修正为 0x7543427748——我的复核确认修正值正确，README 那行是没删干净的残留。

2. GET-GAIN 文档贴错了代码段
DISASM-GET-GAIN-ACT-GAUGE.md 贴出的「getter 24 条指令」，经逐字节比对与构造函数开头 39/40 字节相同（仅 1 字节手抄差），实际是错拿了构造函数的段落，不是 getter 本体。getter 真身就是上面第 ④ 条的两条指令。文档里「纯 TryGetValue 尾调用」的中间过程描述需要复核；不过「getter 无计算」这个最终结论反而更成立了。

🔧 仓库自己抓出的手解三错（值得记一笔）

CTOR-VERIFIED.md 记录了手解 vs capstone 的对照，三处全被抓到：

  • 序言首条：str x29 → str x30（寄存器认错）
  • 布尔掩码：and #3 → and #1（掩码位数错）
  • bl 目标：0x70E43844 → 0x7543427748（imm26 符号位移算错，差了十倍以上）

第三处最要命——如果不校验，后续会沿完全错误的地址查下去。所以才立了「任何手算地址一律先落 raw 过 capstone」的纪律。

5 · 推理链存档 —— 「怎么想的」

hlpatch-reasoning-log 首篇（2026-11-01）讲了一个典型样本：转储里怎么到处都是 44444？

444444 = 0x6C81C = 本局的 ObscuredInt 加解密 key

内存里：[ key = 0x6C81C ][ hidden = key ^ 真实值 ]
真实值 = hidden ^ key

每个 int 都拆成两个字段存，所以每个 ObscuredInt 都会让 1c c8 06 00（钥匙的小端字节）在转储里出现一次。一个训练 7 个 ObscuredInt，五个训练就是 35 次——看起来「怎么全是 44444」，其实是同一把钥匙被反复打印。这类「噪音来源解释」正是该仓的收藏方向。
